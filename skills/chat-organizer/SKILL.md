# 聊天整理助手
使用本 Skill 自带的 scripts/organize.py。将下文的入口替换成此文件所在目录下的脚本绝对路径。使用 Python 3.14。首次运行执行 doctor；完整自检缺条件返回非零，按 checks_missing 准确处理，不重置数据、不盲目重启。doctor --installation 仅用于安装检查，不能代替桌面运行检查；自检不验证登录权限或真实接口通信。

## 先确定整理范围
“整理一下乱标题”未给范围时，不能自行默认20条、只取一小段或立即付费分析。先执行 `py -3.14 <入口> discover`：分页盘点可访问的本机未归档聊天，读取标题元数据和已有缓存，不调用分析模型、不改聊天。展示总量、新候选、已有待确认方案、已处理跳过、超长/待复核数量，并给盘点报告入口，让用户知道范围。
再简短问一次：“先找最近10条需要改名的、20条，还是把当前可读取范围全部检查？”用户已经指定数量或全部时不再询问，直接按其范围推进。

## 按有效改名数量筛选
- “找最近10条乱的”“整理20条”：运行 `scan --count 10` 或 `scan --count 20`。数字表示**需要改名的建议数**，不是选取或读过的聊天数。按最近更新顺序持续检查；保留原题、待判断、延后和已处理项不占名额，直到达到目标或范围耗尽。
- “乱的全部整理”“全部检查一遍”：运行 `scan --all`，遍历当前可访问的本机未归档范围。没有20条上限；始终先预览，不直接修改。告诉用户全量可能需要更多分析，不能把原生侧栏50条窗口当全部。
- 用户明确限定“最近100条里找10条”时用 `scan --count 10 --recent 100`；recent是检查范围，count是有效建议数，不能混用。只有用户给出分析预算时才传 `--max-analysis N`，达到预算必须明确报告停止原因与不足数量，不能冒称目标完成。
- 命令行scan必须指定count或all，不存在隐式数量默认值。不要用旧oneclick或旧扫描函数绕开范围选择。

“乱”的判断基于能否找到内容：开场白/含糊请求当标题、拖长且难辨主题、与实际正文主线不符等。标题虽未采用统一分隔符但内容清楚，不为凑数强行改名；盘点阶段的candidate只是未分析候选，不代表已经判定混乱。

超长聊天单独记为待处理并继续后面的候选，不截断正文冒充全文分析，不让一条超长卡住整批。报告列出所有延后项；尚有延后项时不能声称“全部整理完”。模型执行不确定或错误时保留批次、停止自动重发，说明已完成数量和剩余范围。

## 预览标题与固定命名规则
上述请求仅授权读取与分析，**不授权直接改名**，也不授权建项目、移动聊天。
保存 session_id，展示逐条原题、建议题、摘要与项目建议，明确尚未改名。返回的 title_draft 是未批准的标题草案。
报告先列需要改名的清单，再概述保留、复用、保护跳过、待判断、超长延后、未检查与停止原因。保留原题不等于“以前已处理”，两者必须分开说。每条原题和ID在本地报告中可查，不只报“看了8条”。
命名规则保存在 data_dir/naming-policy.json。首次采用“对象｜具体用途”，最长32字，清楚的旧标题保留；以后批次读取同一规则，不凭临时偏好换格式。用户要求换规则时先展示并确认，修改该文件且递增version；已生成方案沿用自己的规则快照，不重调模型、不追改已处理聊天。详见 references/naming-and-review.md。
回看执行 `report --session-id ID`。进程中断后以原session_id及原范围参数续接；终止原因已记录的会话只回读，不自动重发失败批次。另开新整理任务时自动复用未执行且标题/更新时间/规则一致的旧方案，保持原始来源；变更或不确定的缓存列待复核，不重调模型。已经锁定/尝试执行的仍跳过。
旧v0.3.0中断会话不要直接重跑旧scan；使用新范围入口，自动复用其已分析结果，未分析候选继续检查。
模型读取选中聊天的可见正文，标题和项目建议同批生成；本地不等于零用量或完全离线。

## 确认标题后改名
等用户审阅具体标题，支持逐条修订、保留、部分批准。复制标题草案另存批准文件，保留session_id、title_digest；approved=true，user_confirmation记录真实确认，不能以“整理一下”代替。
decisions只放确认过的聊天，action为rename或keep；rename的title必须满足该会话命名规则。review项先解决再批准。
执行：`apply-titles --session-id ID --approval 标题批准文件绝对路径`。
此步骤没有模型调用、不归项目。回读逐条结果；失败查回执、不自动重放。部分批准后，其余标题继续等待确认；全部确认完成才进入项目阶段。
标题确认不等于项目确认。改名后重新给出项目建议与分组草案，等待用户对具体去向的第二次确认。

## 确认后归类
用户确认具体报告或提出调整后，另存批准文件，保留 session_id 和 review_digest；approved=true，user_confirmation 必须记录真实用户确认。只涉及该会话成功命名的聊天，禁止伪造批准。
destination 为已有项目ID、keep、null 或 new:项目名。杂聊默认 keep；只有用户确认移出原项目才设 null。允许部分批准。
已有、新建或混合项目统一执行：`apply --session-id ID --approval 批准文件绝对路径`。
**创建项目是本工具负责的动作，不能让用户去菜单里手动新建，也不能只给创建建议就停止。** 用户确认new:项目名后，apply自动检查同名项目、准备目录、调用官方创建接口、回读并继续归类。默认新目录在data_dir/projects；批准文件可用project_roots指定目录列表，给用户展示方案时一并说明采用的位置。唯一同名项目默认复用已有根目录，不重复建项目。
新项目执行前阅读 references/projects-and-recovery.md。若返回project_creation.state=desktop_registration_required，项目已经在后端存在：沿用返回ID及roots_file准备桌面登记修复，不再创建，不让用户手动补建。确需退出客户端时，先准备修复程序，再一次性说明必要操作。没有离线修复授权时不能启动修复。
完成后逐条报告实际结果。归类读取缓存，不重新分析。

## 保护与交付
- 所有已处理记录持续跳过；升级不能清空数据目录。用户点名旧聊天修改作为独立任务。
- 只使用安装的原版官方工具和执行器真实环境，不输出连接凭据，不修改插件。
- 写前意图、冲突检查、独立回读、保护置顶；失败保留证据，核查实际状态后再决定，不自动重放。
- 不操作屏幕，不排程，不直接写生产SQLite；离线配置修复仅在明确授权、版本与守卫都通过后执行。
- 区分建议、已执行、后端创建、原生目录可见和截图验收；不得混称。
- 报告放配置指定的正式输出目录。先给目录绝对路径，再给逐条报告链接。遵循用户位置偏好。
- 环境与缓存说明见 references/runtime.md。
